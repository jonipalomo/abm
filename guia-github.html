ABM de Alumnos · Repositorio en GitHub

Cómo comparten el código los dos programadores

Guía práctica de los comandos de Git y GitHub que backend y frontend usan todos los días para trabajar sobre el mismo repositorio sin pisarse el código.

Concepto

Las cuatro paradas del código fuente

Antes de los comandos, conviene tener claro por dónde pasa un cambio hasta llegar al repositorio de GitHub que comparten los dos:

Directorio de trabajo los archivos que editás en tu editor git status
→
↓
Área de preparación lo que marcaste para el próximo commit git add
→
↓
Repositorio local historial guardado en tu máquina git commit
→
↓
GitHub (remoto) donde lo ve tu compañero git push

Para traer lo que subió el compañero pasa lo mismo, pero al revés: git pull baja los cambios de GitHub directo a tu directorio de trabajo.

Paso previo

Configuración inicial (una sola vez por máquina)

Cada programador la corre una vez al empezar a trabajar en una computadora nueva:

git config --global user.name "Tu Nombre" Identifica quién hizo cada commit
git config --global user.email "tu@email.com" Debe coincidir con el email de tu cuenta de GitHub
git clone https://github.com/jonipalomo/abm.git Trae una copia completa del repositorio (una sola vez)
Después del clone Instalar dependencias y preparar la base antes de programar: pip install -r requirements.txt && python manage.py migrate

Referencia

Comandos esenciales del día a día

Los que se usan constantemente, agrupados por lo que hacen:

Ver el estado de tus cambios

git status Qué archivos cambiaste, cuáles están preparados para commit
git diff Qué líneas exactas cambiaron, línea por línea
git log --oneline Historial de commits, uno por línea

Guardar cambios

git add nombre-archivo.py Prepara un archivo puntual para el commit
git add . Prepara todos los archivos modificados (usar con cuidado)
git commit -m "mensaje claro" Guarda los cambios preparados en el historial local

Ramas

git branch Lista las ramas locales
git checkout -b nombre-rama Crea una rama nueva y te parás en ella
git checkout main Volver a la rama principal
git merge nombre-rama Integra los cambios de una rama en la actual

Sincronizar con GitHub

git pull Trae y aplica los cambios que subió tu compañero
git push Sube tus commits al repositorio remoto
git push -u origin nombre-rama Sube una rama nueva por primera vez y la vincula

Trabajo en equipo

Backend y frontend trabajando al mismo tiempo

Cada uno arranca su propia rama desde main, así ninguno bloquea al otro:

Programador Backend

1. Actualizar main y crear rama

git checkout main git pull git checkout -b backend-validacion-dni

2. Editar alumnos/models.py, forms.py, views.py

git add alumnos/ git commit -m "Validar formato de DNI"

3. Subir la rama y abrir Pull Request

git push -u origin backend-validacion-dni
Programador Frontend

1. Actualizar main y crear rama

git checkout main git pull git checkout -b frontend-landing

2. Editar templates/home.html, style.css

git add templates/ static/ git commit -m "Rediseñar landing page"

3. Subir la rama y abrir Pull Request

git push -u origin frontend-landing
Antes de empezar a programar cada día Pararse en main y correr git pull para no trabajar sobre una versión vieja del código.

Paso a paso

Ejemplo completo: subir un cambio y mergearlo

1

Crear la rama

git checkout -b frontend-landing

2

Programar y revisar qué cambió

git status y git diff antes de guardar

3

Preparar y commitear

git add . luego git commit -m "Rediseñar landing page"

4

Subir la rama a GitHub

git push -u origin frontend-landing

5

Abrir un Pull Request en github.com

Botón "Compare & pull request" que aparece en el repositorio. Describir qué se hizo y por qué.

6

El compañero revisa y aprueba

Lee el diff, comenta si algo no queda claro, aprueba el PR.

7

Merge a main (desde GitHub)

Botón "Merge pull request". Después, borrar la rama ya integrada.

8

Ambos actualizan su copia local

git checkout main y git pull

Cuando pasa

Resolver un conflicto de merge

Pasa cuando los dos tocaron la misma línea del mismo archivo en ramas distintas. Git no puede decidir solo cuál versión es la correcta, así que lo marca y lo tenés que resolver a mano.

git pull Si hay conflicto, Git avisa y marca los archivos afectados
git status Lista los archivos con conflicto sin resolver
git add archivo-resuelto.py Marca el archivo como resuelto después de editarlo a mano
git commit Cierra el merge una vez resueltos todos los conflictos
Dentro del archivo en conflicto Git deja marcas <<<<<<< HEAD, ======= y >>>>>>> alrededor de las dos versiones. Hay que dejar el código final correcto y borrar esas marcas antes de guardar.
