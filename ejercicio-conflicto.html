Provocar y resolver un conflicto de merge, a propósito

Los dos van a editar la misma línea del mismo archivo sin avisarse, para que Git no pueda decidir solo qué versión es la correcta. Después lo van a resolver a mano. Es la mejor forma de perderle el miedo a la palabra "conflict".

Antes de empezar

Objetivo del ejercicio

✓

Que cada uno viva, con sus propias manos, el ciclo completo: divergencia → conflicto → resolución → merge limpio. No importa el contenido que se pierda o se pise: el archivo que van a usar (README.md) es de bajo riesgo, pensado para esto.

Antes de arrancar, mirá cómo se ve un merge con conflicto resuelto paso a paso:

Requisitos

Preparación

Los dos programadores, cada uno en su propia máquina y con su propio clon del repositorio:

git checkout mainPararse en la rama principal
git pullTraer la última versión antes de arrancar

Confirmá que en tu README.md, cerca del principio, está esta línea (es el "blanco" del ejercicio):

**Última actualización a cargo de:** _(completar)_

Manos a la obra

Paso a paso

Sigan el orden. Lo importante es que frontend cree su rama antes de que backend mergee la suya — así los dos parten del mismo README viejo y el conflicto queda garantizado.

1

Backend crea su rama

Backend

Desde main actualizado:

git checkout -b backend-actualizar-estado
2

Frontend crea su rama

Frontend

También desde main, sin esperar a que backend termine:

git checkout main
git checkout -b frontend-actualizar-estado
3

Backend edita la línea

Backend

En README.md, reemplazar _(completar)_ por:

**Última actualización a cargo de:** Backend

Guardar y confirmar el cambio:

git add README.md
git commit -m "Actualizo estado del README"
4

Frontend edita la misma línea

Frontend

En su propia copia (todavía no vio el cambio de backend), reemplazar _(completar)_ por:

**Última actualización a cargo de:** Frontend
git add README.md
git commit -m "Actualizo estado del README"
5

Backend sube y mergea primero

Backend
git push -u origin backend-actualizar-estado

Abrir Pull Request en GitHub → mergearlo a main. Ahora main ya tiene la versión de backend.

6

Frontend sube su rama

Frontend
git push -u origin frontend-actualizar-estado

Todavía no hay conflicto: el conflicto aparece recién cuando frontend intenta juntar su rama con el main ya actualizado.

!

Frontend trae main y aparece el conflicto

Acá pasa
git checkout main
git pull
git checkout frontend-actualizar-estado
git merge main

Git responde algo como:

Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

El momento clave

Resolver el conflicto

Al abrir README.md, en vez de la línea de siempre vas a encontrar esto:

<<<<<<< HEAD **Última actualización a cargo de:** Frontend ======= **Última actualización a cargo de:** Backend >>>>>>> main

Lo de arriba (HEAD) es la versión de la rama en la que estás parado; lo de abajo (main) es la que viene de afuera. Hay que decidir qué queda y borrar las tres marcas.

8

Editar a mano el resultado final

Frontend

Por ejemplo, dejando registro de los dos en vez de pisarse:

**Última actualización a cargo de:** Backend y Frontend

Borrar por completo las líneas <<<<<<< HEAD, ======= y >>>>>>> main. Solo debe quedar el texto final, sin marcas.

9

Marcar como resuelto y cerrar el merge

Frontend
git add README.md
git commit

Git ya trae un mensaje de merge sugerido; se puede dejar tal cual o editarlo, y guardar.

10

Subir la rama resuelta

Frontend
git push

Abrir el Pull Request de frontend-actualizar-estado hacia main y mergearlo: ya no debería mostrar conflictos, porque se resolvió en tu máquina en el paso anterior.

Cierre

Verificar y limpiar

git checkout mainAmbos vuelven a la rama principal
git pullTraen la versión final ya mergeada
git log --oneline --graphVer cómo quedó el historial con las dos ramas y el merge
git branch -d backend-actualizar-estadoBorrar la rama local ya usada
git push origin --delete backend-actualizar-estadoBorrar también la rama remota (ídem con la de frontend)
Por qué pasó esto Los dos partieron del mismo main viejo y modificaron la misma línea sin coordinarse. En un proyecto real esto se evita comunicándose antes de tocar un archivo compartido, o haciendo git pull más seguido. El conflicto no es un error grave: es Git protegiendo el trabajo de los dos.

Antes de dar el ejercicio por terminado

Checklist

  • Vi aparecer el mensaje "CONFLICT" en la terminalNo lo evité ni lo cancelé con git merge --abort
  • Identifiqué las tres marcas dentro del archivo<<<<<<< HEAD, =======, >>>>>>> main
  • Edité el contenido final a mano y borré las marcasEl archivo quedó sin ningún rastro de <<< o >>>
  • Cerré el merge con git add + git commitY subí la rama con git push
  • Confirmé en GitHub que el Pull Request mergeó sin conflictosPorque ya lo habíamos resuelto en la máquina
  • Borré las ramas de pruebaLocal y remota, para no dejar basura en el repositorio
