Guía de comandos por nivel

Los mismos comandos de Git, agrupados según quién los necesita: lo mínimo para arrancar, y el flujo del día a día para cada uno de los dos programadores que trabajan en paralelo sobre el repositorio.

Nivel inicial Programador 1 Programador 2 Unificar el trabajo

Nivel inicial

Lo mínimo para empezar a trabajar

Estos comandos alcanzan para clonar el proyecto, ver qué cambiaste y guardar tu trabajo. Es la base que necesitan los dos programadores antes de dividirse tareas.

Una sola vez por máquina

git config --global user.name "Tu Nombre" Identifica quién hizo cada commit
git config --global user.email "tu@email.com" Debe coincidir con el email de tu cuenta de GitHub
git clone https://github.com/jonipalomo/abm.git Trae una copia completa del repositorio

Ver en qué estás parado

git status Qué archivos cambiaste y en qué rama estás
git diff Qué líneas exactas cambiaron, línea por línea
git log --oneline Historial de commits, uno por línea

Guardar y sincronizar

git add nombre-archivo.py Prepara un archivo puntual para el commit
git commit -m "mensaje claro" Guarda los cambios preparados en el historial local
git pull Trae los cambios que subió tu compañero
git push Sube tus commits al repositorio remoto
Con esto ya podés trabajar Si recién estás empezando, quedate con estos ocho comandos. El resto de la guía (ramas, Pull Requests) llega cuando dos personas tocan el mismo repositorio al mismo tiempo.

Programador 1 · Backend

Flujo del día a día, con código real

Además de los comandos del nivel inicial, cuando trabajás en paralelo con tu compañero necesitás manejar tu propia rama. Backend trabaja sobre alumnos/models.py, forms.py y views.py.

Ejemplo de tarea: agregar el campo "teléfono" al alumno Backend define el campo en el modelo y lo habilita en el formulario. En la sección de Programador 2 se ve cómo frontend lo muestra en el listado, en paralelo, sin pisar estos mismos archivos.

1. Empezar el día actualizado y crear tu rama

terminal
git checkout maingit pullgit checkout -b programador1-telefono-alumno

2. Agregar el campo en el modelo

alumnos/models.py modificar
class Alumno(models.Model):    nombre = models.CharField(max_length=100)    apellido = models.CharField(max_length=100)    dni = models.CharField(max_length=15, unique=True)    email = models.EmailField(blank=True)    telefono = models.CharField(max_length=20, blank=True)    curso = models.ForeignKey(        Curso,        on_delete=models.PROTECT,        related_name='alumnos'    )

3. Habilitarlo en el formulario

alumnos/forms.py modificar
class AlumnoForm(forms.ModelForm):    class Meta:        model = Alumno        fields = ['nombre', 'apellido', 'dni', 'email', 'telefono', 'curso', 'fecha_nacimiento', 'activo']
No hace falta tocar alumno_form.html: ese template recorre {% for field in form %}, así que cualquier campo nuevo del formulario aparece solo.

4. Generar y aplicar la migración

terminal
python manage.py makemigrations alumnospython manage.py migratepython manage.py runserver
makemigrations crea un archivo nuevo dentro de alumnos/migrations/ (algo como 0004_alumno_telefono.py). Ese archivo también se commitea: sin él, la migración no existe para tu compañero ni para el servidor.

5. Guardar y subir solo lo que tocaste

terminal
git statusgit add alumnos/models.py alumnos/forms.py alumnos/migrations/git commit -m "Agregar campo telefono a Alumno"git push -u origin programador1-telefono-alumno
Antes de crear una rama nueva Siempre pasá primero por git checkout main y git pull. Si creás la rama desde un main viejo, tu Pull Request va a arrastrar cambios que ya no hacen falta.

Programador 2 · Frontend

Mismo flujo, tu propia rama y tus propios archivos

Es la misma rutina que Programador 1: la diferencia está en que trabajás en paralelo sobre otra rama y, en lo posible, sobre archivos distintos — en este proyecto, los que están en templates/ y static/.

Mismo ejemplo, del lado del frontend Mientras Programador 1 agrega el campo telefono al modelo (sección Programador 1), acá se muestra cómo hacerlo visible en el listado de alumnos.

1. Empezar el día actualizado y crear tu rama

terminal
git checkout maingit pullgit checkout -b programador2-mostrar-telefono

2. Agregar la columna en el listado

alumnos/templates/alumnos/alumno_list.html modificar
<tr>    <th>Apellido</th>    <th>Nombre</th>    <th>DNI</th>    <th>Teléfono</th>    <th>Curso</th>    <th>Activo</th>    <th></th></tr>
alumnos/templates/alumnos/alumno_list.html modificar
<tr>    <td>{{ alumno.apellido }}</td>    <td>{{ alumno.nombre }}</td>    <td>{{ alumno.dni }}</td>    <td>{{ alumno.telefono|default:"—" }}</td>    <td>{{ alumno.curso }}</td>
Esta columna solo va a mostrar datos reales una vez que la rama de backend con el campo telefono esté mergeada a main. Hasta entonces no rompe nada: Django simplemente muestra vacío.

3. Probar y guardar

terminal
python manage.py runservergit statusgit add alumnos/templates/alumnos/alumno_list.htmlgit commit -m "Mostrar telefono en el listado de alumnos"git push -u origin programador2-mostrar-telefono

4. Cuando el otro ya mergeó algo a main

git checkout main Pararte en la rama principal
git pull Traer el cambio que ya se integró (por ej. el campo telefono)
git checkout programador2-mostrar-telefono Volver a tu rama
git merge main Traer ese cambio a tu rama antes de seguir, para evitar sorpresas
Si aparece un conflicto Git va a marcar el archivo afectado. Abrilo, dejá la versión final correcta borrando las marcas <<<<<<< / ======= / >>>>>>>, después git add archivo y git commit. El detalle completo está en la guía de Git y GitHub.

Unificar el trabajo

Cómo se combinan las dos ramas en main

Programador 1 y Programador 2 trabajaron en paralelo, en ramas separadas, sobre archivos distintos. Unificar el trabajo es el proceso de llevar los dos resultados a main sin perder nada. Así se ve el recorrido completo:

main rama de Programador 1 rama de Programador 2

Diez pasos, en este orden. Cada número es un commit real que va a quedar en el historial (o el merge que lo integra):

1

Programador 1 crea su rama Programador 1

Parte de main actualizado.

terminal
git checkout maingit pullgit checkout -b programador1-telefono-alumno
2

Programador 2 crea la suya, en paralelo Programador 2

No espera a que Programador 1 termine: arranca al mismo tiempo, desde el mismo punto de main.

terminal
git checkout maingit pullgit checkout -b programador2-mostrar-telefono
3

Commit 1: campo nuevo en el modelo y el formulario Programador 1

Edita alumnos/models.py y alumnos/forms.py como en la sección Programador 1, corre makemigrations/migrate, y guarda.

terminal
git add alumnos/models.py alumnos/forms.py alumnos/migrations/git commit -m "Agregar campo telefono a Alumno"
4

Sube la rama y abre el Pull Request #1 Programador 1

terminal
git push -u origin programador1-telefono-alumno

En github.com aparece el botón "Compare & pull request". Programador 2 (u otro revisor) lo revisa y lo aprueba.

5

Commit 2 (merge): Pull Request #1 entra a main Compartido

Se hace con el botón "Merge pull request" en GitHub — ese click crea el commit de merge. Si prefieren hacerlo por consola en vez de la web, es lo mismo:

terminal
git checkout maingit merge programador1-telefono-alumno --no-ff -m "Merge pull request #1: Agregar campo telefono a Alumno"git push
6

Commit 3 (merge): sincronizar con el cambio de backend Programador 2

Antes de seguir, Programador 2 trae el campo telefono a su propia rama. Si algo choca, el conflicto aparece acá — se resuelve como en la guía de conflictos.

terminal
git checkout maingit pullgit checkout programador2-mostrar-telefonogit merge main -m "Merge branch 'main' into programador2-mostrar-telefono"
7

Commit 4: mostrar el campo en el listado Programador 2

Edita alumno_list.html como en la sección Programador 2. Ahora sí, al probar en runserver, el teléfono ya tiene datos reales para mostrar.

terminal
git add alumnos/templates/alumnos/alumno_list.htmlgit commit -m "Mostrar telefono en el listado de alumnos"
8

Sube la rama y abre el Pull Request #2 Programador 2

terminal
git push -u origin programador2-mostrar-telefono
9

Commit 5 (merge): Pull Request #2 entra a main Compartido

Mismo mecanismo que el paso 5: botón "Merge pull request" en GitHub, o por consola:

terminal
git checkout maingit merge programador2-mostrar-telefono --no-ff -m "Merge pull request #2: Mostrar telefono en el listado"git push
10

Ambos actualizan su copia local Compartido

terminal
git checkout maingit pull

Resultado: el modelo tiene el campo, el formulario lo pide y el listado lo muestra — el trabajo de los dos quedó unificado en un solo main, sin que nadie pisara el archivo del otro.

Por qué no hubo conflictos "de verdad" en este ejemplo Backend y frontend tocaron archivos distintos (alumnos/models.py / forms.py por un lado, alumno_list.html por el otro). El único punto donde podría haber fricción es el paso 6 (git merge main), y solo pasa algo si los dos editaron la misma línea del mismo archivo. Repartir bien las tareas antes de empezar es la mejor forma de evitar conflictos.
