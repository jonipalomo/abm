ABM de Alumnos · Django

Antes de programar, modelamos

Esta guía reúne los conceptos base para entender cómo está armado el proyecto y cómo seguir modelándolo entre los dos: quién programa el backend, quién el frontend, y dónde encaja cada pieza.

Concepto 1

El patrón MVT de Django

Django organiza el código en tres piezas que se reparten el trabajo. No es exactamente el clásico MVC, pero se le parece mucho: acá se llama Modelo – Vista – Template.

Navegador hace un pedido HTTP (una URL)
→
↓
Vista (View) decide qué hacer: lee, valida, guarda
→
↓
Modelo (Model) habla con la base de datos
Vista (View) con los datos ya listos...
→
↓
Template (HTML) arma la página que se ve
→
↓
Navegador muestra el resultado

Modelo

Define qué datos existen y cómo se guardan. En este proyecto: alumnos/models.py. Es el plano de la tabla en la base de datos.

Vista

Contiene la lógica: qué pasa cuando alguien entra a una URL. En este proyecto: alumnos/views.py.

Template

Es lo que se ve: HTML con partes dinámicas. En este proyecto: los .html de templates/.

Concepto 2

ABM es lo mismo que CRUD

"ABM" (Alta, Baja, Modificación) es el nombre que usamos en castellano para lo que en inglés se conoce como CRUD (Create, Read, Update, Delete). Son las cuatro operaciones básicas que se pueden hacer sobre cualquier dato.

A

Alta / Create

Crear un alumno nuevo. Vista: AlumnoCreateView

C

Consulta / Read

Ver el listado o un detalle. Vista: AlumnoListView

M

Modificación / Update

Editar datos existentes. Vista: AlumnoUpdateView

B

Baja / Delete

Eliminar un registro. Vista: AlumnoDeleteView

Concepto 3

Modelar una entidad: el caso "Alumno"

Modelar es decidir qué atributos tiene una entidad y de qué tipo es cada uno, antes de escribir una sola línea de vista o de template. Así quedó modelado Alumno en este proyecto:

Alumno
  • identero, autogenerado
  • nombretexto (100)
  • apellidotexto (100)
  • dnitexto (15), único
  • emailemail, opcional
  • cursotexto (50)
  • fecha_nacimientofecha, opcional
  • activosí/no, default sí
  • creadofecha y hora, automático

El campo id es la clave primaria: identifica sin ambigüedad a cada alumno y Django lo crea solo, no hace falta declararlo. La restricción "único" en dni evita que se carguen dos alumnos con el mismo documento.

Concepto 4

Anatomía del proyecto: quién toca qué

Cada archivo tiene una responsabilidad. Así se reparten entre backend y frontend:

alumnos/models.py Define la entidad Alumno y sus campos Backend
alumnos/forms.py Valida los datos que llegan del formulario Backend
alumnos/views.py Lógica: qué hace cada URL (listar, crear, editar, borrar) Backend
alumnos/urls.py Mapa de rutas del ABM Backend
alumnos/admin.py Configura el panel /admin/ Backend
templates/base.html Esqueleto visual común (header, nav, footer) Frontend
templates/home.html Landing page del proyecto Frontend
alumnos/templates/alumnos/*.html Listado, formulario y confirmación de borrado Frontend
static/css/style.css Estilos visuales del sitio Frontend
config/settings.py Configuración general del proyecto Django Compartido
manage.py Punto de entrada para correr comandos Compartido

Concepto 5

El recorrido de una petición: dar de alta un alumno

Siguiendo el ejemplo de "crear un alumno nuevo", así viajan los datos por todo el proyecto:

1

Click en "+ Nuevo alumno"

El navegador pide la página /alumnos/nuevo/.

2

Django resuelve la URL

config/urls.py deriva a alumnos/urls.py, que la asocia a AlumnoCreateView.

3

La vista muestra el formulario

AlumnoCreateView usa AlumnoForm y renderiza alumno_form.html (vacío, primera vez).

4

El usuario completa y envía

El navegador manda los datos por POST a la misma URL.

5

Se valida y se guarda

AlumnoForm valida (¿DNI único? ¿campos obligatorios completos?) y, si está todo bien, models.py guarda el registro en la base de datos.

6

Redirección al listado

La vista redirige a /alumnos/ y muestra un mensaje de éxito.

Concepto 6

Trabajar de a dos sobre el mismo repositorio

Backend y frontend avanzan en paralelo sin pisarse el trabajo usando ramas de Git y Pull Requests (PR):

1

Crear una rama desde main

git checkout -b frontend-landing (o backend-validacion-dni)

2

Programar en esa rama

Commits chicos y frecuentes, con mensajes claros de qué se hizo.

3

Subir la rama

git push -u origin frontend-landing

4

Abrir un Pull Request en GitHub

Explicar qué cambió y por qué, para que el compañero lo entienda rápido.

5

Revisión cruzada

El otro desarrollador lee el código, comenta o aprueba.

6

Merge a main

Una vez aprobado, se integra y ambos actualizan su copia local con git pull.

Concepto 7

Próximo desafío de modelado: relacionar entidades

Hoy curso es solo un campo de texto dentro de Alumno. El siguiente paso natural para seguir modelando es convertirlo en una entidad propia y relacionarla con Alumno mediante una clave foránea (Foreign Key): un curso tiene muchos alumnos, y cada alumno pertenece a un solo curso.

Curso
  • idPK
  • nombretexto
  • turnotexto
1
N
Alumno
  • idPK
  • ...otros campos
  • curso_idFK → Curso

La lectura es: "un Curso tiene muchos Alumnos" (relación uno-a-muchos, 1:N). Es el mismo tipo de decisión de modelado que ya se tomó con Alumno, aplicada a una entidad nueva.

Checklist para encarar este desafío

  • Backend: crear el modelo Curso Nuevo modelo en alumnos/models.py (o una app nueva cursos) con nombre y turno.
  • Backend: reemplazar el campo curso Cambiarlo por curso = models.ForeignKey(Curso, on_delete=models.PROTECT) y generar la migración.
  • Frontend: actualizar el formulario y el listado El campo pasa a ser un desplegable (select) en vez de texto libre; mostrar el nombre del curso en la tabla.
  • En conjunto: revisar el flujo completo Probar alta, edición y listado de alumnos con la nueva relación, y registrar el cambio en el README.
